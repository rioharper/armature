# Bundled MCP server startup (#35)

Research note for wayfinder ticket [#35](https://github.com/rioharper/armature/issues/35): every session in a project that is not on SolidWorks opens with a red "failed to connect" for the plugin's bundled `solidworks` MCP server. Verified against the Claude Code docs at code.claude.com (the docs.claude.com URLs 301-redirect there), the plugin manifest schema, this repo's files, and a live `claude mcp list` on Claude Code 2.1.267. Date: 2026-09-10.

## Answer

Claude Code gives a plugin no way to ship an MCP server that stays quiet when its host application is absent: a plugin's `.mcp.json` servers "start automatically when the plugin is enabled", stdio servers connect at session start (the only deferred-connection paths are the discovery cache, which is remote-HTTP/SSE-only and off by default, and on-demand start in web sessions), there is no per-server enable flag in the manifest, and the only per-server switch is the user's own `/mcp` toggle, recorded per project in `~/.claude.json` under `disabledMcpServers`. `enabledMcpjsonServers` / `disabledMcpjsonServers` / `enableAllProjectMcpServers` govern approval of a *project's* `.mcp.json`, not plugin servers, and `--mcp-config --strict-mcp-config` is a per-launch CLI override. The server itself is already "per-tool no-session" by design: `server.py` never touches SolidWorks at import or startup; every tool calls `sw.attach()`, which raises `SwNotRunning("SolidWorks is not running. Start SolidWorks, open the document, then retry.")`. The red banner is therefore never about SolidWorks being closed. It comes from the *process* failing to start: `uv` is not on PATH (true on this machine: `Get-Command uv` finds nothing, and both servers report `CONNECTION_CLOSED`), or the host is not Windows (the `pywin32; sys_platform == 'win32'` marker leaves `import pythoncom` unsatisfied and the script exits at import). Given those constraints, the recommended fix is to stop bundling the server in the plugin's `.mcp.json` and make it opt-in at the moment the user chooses SOLIDWORKS in `/armature:init`: init writes a project-scoped `.mcp.json` (or offers `claude mcp add --scope user`) pointing at the server, so only SolidWorks projects ever attempt the connection. The runner-up is to split the server into a second plugin in the same marketplace with `defaultEnabled: false`.

## Facts

Each fact carries the source that owns it. Quotes are verbatim.

### What the plugin system does with a bundled server

1. **Plugin MCP servers start with the plugin, at session start.** "Plugin MCP servers start automatically when the plugin is enabled" — [plugins-reference#mcp-servers](https://code.claude.com/docs/en/plugins-reference#mcp-servers). "At session startup, Claude Code connects the servers for enabled plugins automatically. In `/mcp`, a remote (HTTP or SSE) plugin server you've used before can show the `cached` status instead" — [mcp#plugin-provided-mcp-servers](https://code.claude.com/docs/en/mcp#plugin-provided-mcp-servers).
2. **No per-server enable flag exists in the manifest.** The manifest schema's `mcpServers` field is "MCP config paths or inline config" (string, array, or object); the only enablement field is plugin-wide `defaultEnabled` — [plugins-reference#plugin-manifest-schema](https://code.claude.com/docs/en/plugins-reference#plugin-manifest-schema), [#default-enablement](https://code.claude.com/docs/en/plugins-reference#default-enablement): "Set `defaultEnabled: false` in `plugin.json` to ship a plugin that installs disabled. The user turns it on with `claude plugin enable <plugin>` or the `/plugin` interface. Use this for plugins that add cost or scope a user should opt into, such as one that connects to an external service." A marketplace entry can carry the same field and "Takes precedence over the same field in the plugin's `plugin.json`" — [plugin-marketplaces optional fields](https://code.claude.com/docs/en/plugin-marketplaces#optional-plugin-fields).
3. **Users can toggle a plugin server off, per project, from their side only.** "You add and remove plugin servers by installing or uninstalling the plugin, not with `/mcp` commands. You can still toggle an installed plugin server off in `/mcp`, which stops Claude Code from connecting to it without removing the plugin" — [mcp#plugin-provided-mcp-servers](https://code.claude.com/docs/en/mcp#plugin-provided-mcp-servers). The toggle is "recorded per project in `~/.claude.json`" in `disabledMcpServers`, "an opt-out list for user-configured servers, plugin servers, ..." — [mcp#disable-a-server-without-removing-it](https://code.claude.com/docs/en/mcp#disable-a-server-without-removing-it). `claude mcp list` then shows "`⊘ Disabled for this project (re-enable via /mcp)`" without connecting — [mcp#server-status](https://code.claude.com/docs/en/mcp#server-status). `~/.claude.json` is not a settings file a plugin or repo can ship, so this is a workaround the user repeats per project, not a fix the plugin can make.
4. **`enabledMcpjsonServers` / `disabledMcpjsonServers` / `enableAllProjectMcpServers` are about a project's `.mcp.json`, not plugin servers.** `disabledMcpjsonServers`: "Reject specific servers defined in a project's `.mcp.json` file so Claude Code never connects them or asks you to approve them. A rejection in any settings file applies, including a project `.claude/settings.json` checked into the repository." `enabledMcpjsonServers`: "Approve specific servers defined in project `.mcp.json` files so Claude Code connects them without asking." — [settings-reference#disabledmcpjsonservers](https://code.claude.com/docs/en/settings-reference#disabledmcpjsonservers), [#enabledmcpjsonservers](https://code.claude.com/docs/en/settings-reference#enabledmcpjsonservers), [#enableallprojectmcpservers](https://code.claude.com/docs/en/settings-reference#enableallprojectmcpservers). And explicitly: "`disabledMcpServers` and `enabledMcpServers` are unrelated to `enabledMcpjsonServers` and `disabledMcpjsonServers`, which control approval of servers defined in a project's `.mcp.json` file" — [mcp#disable-a-server-without-removing-it](https://code.claude.com/docs/en/mcp#disable-a-server-without-removing-it).
5. **`--mcp-config` / `--strict-mcp-config` are per-launch CLI overrides.** `--strict-mcp-config`: "Only use MCP servers from `--mcp-config`, ignoring all other MCP configurations" — [cli-reference](https://code.claude.com/docs/en/cli-reference). Useful for a single session, not a plugin-side lever.
6. **`claude mcp add` scopes** are local (default, "current project only, private to you"), project (`.mcp.json`, "shared via .mcp.json in version control"), and user ("all your projects, private to you"); precedence is local > project > user > plugin-provided > claude.ai connectors — [mcp#mcp-installation-scopes](https://code.claude.com/docs/en/mcp#mcp-installation-scopes), [#scope-hierarchy-and-precedence](https://code.claude.com/docs/en/mcp#scope-hierarchy-and-precedence). Project-scoped servers need a one-time approval: "Claude Code prompts for approval in interactive sessions before using project-scoped servers from `.mcp.json` files"; approving writes `enabledMcpjsonServers` to `.claude/settings.local.json` — [mcp#project-scope](https://code.claude.com/docs/en/mcp#project-scope), [settings-reference#enabledmcpjsonservers](https://code.claude.com/docs/en/settings-reference#enabledmcpjsonservers).
7. **`userConfig` can prompt at enable time but cannot omit a server.** Values substitute as `${user_config.KEY}` "in MCP and LSP server configs and hook commands"; the field is for values, not for conditionally declaring components — [plugins-reference#user-configuration](https://code.claude.com/docs/en/plugins-reference#user-configuration). A `not configured` placeholder that skips connection exists only for remote servers: "A remote server whose configuration has an empty `url` shows as `not configured` ... and Claude Code doesn't attempt to connect to it. A plugin can include a placeholder entry like this for a connector you configure later" — [mcp#server-status-detail](https://code.claude.com/docs/en/mcp#server-status-detail). There is no stdio equivalent.

### Lazy or deferred startup

8. **Tool search defers tool *definitions*, not *connections*.** "Tool search is enabled by default: MCP tools are deferred and discovered on demand" — [mcp#configure-tool-search](https://code.claude.com/docs/en/mcp#configure-tool-search). Startup itself is non-blocking: "MCP startup is non-blocking by default: servers connect in the background and their tools become available as they finish" — [env-vars `MCP_CONNECTION_NONBLOCKING`](https://code.claude.com/docs/en/env-vars). So the failure never delays the session; it is reported.
9. **Connect-on-first-use exists only for remote servers via the discovery cache, and it is off by default.** "With the cache on, a remote HTTP or SSE server you've used before can show the `cached` status, and Claude Code connects it on its first tool call instead of at startup. The cache is off by default unless a gradual rollout has enabled it for your account" — [env-vars `MCP_DISCOVERY_CACHE`](https://code.claude.com/docs/en/env-vars). Our server is stdio, so this path is closed to it.
10. **On-demand start of a plugin server is web-session-only.** "In web sessions, an MCP call to a plugin server that isn't connected yet, such as right after an idle session wakes, starts the server on demand and waits for it to connect" — [mcp#plugin-provided-mcp-servers](https://code.claude.com/docs/en/mcp#plugin-provided-mcp-servers).
11. **Why the failure is loud every session.** "With tool search, Claude Code tells Claude which server failed and its connection error, so Claude reports the connection failure in its response" — [mcp#how-claude-learns-that-a-server-failed](https://code.claude.com/docs/en/mcp#how-claude-learns-that-a-server-failed). Stdio servers get no retry: "Stdio servers are local processes, and Claude Code doesn't reconnect them automatically" — [mcp#automatic-reconnection](https://code.claude.com/docs/en/mcp#automatic-reconnection).

### What this repo does today and why it fails

12. **Config.** `.mcp.json` at the plugin root declares one stdio server: `uv run ${CLAUDE_PLUGIN_ROOT}/mcp/solidworks/server.py` (file: `.mcp.json`; the installed copy at `~/.claude/plugins/cache/armature-plugins/armature/1.2.1/.mcp.json` is identical). `.claude-plugin/plugin.json` has no `mcpServers`, no `defaultEnabled`, no `userConfig`.
13. **Startup path of `server.py`.** The PEP 723 header requires `mcp[cli]>=2,<3` and `pywin32; sys_platform == 'win32'` (`mcp/solidworks/server.py` lines 1-4). The module imports `sw` at load, and `sw.py` imports `pythoncom` and `win32com.client` at load (lines 4-6). `MCPServer("solidworks")` is constructed and `mcp.run()` serves stdio; nothing contacts SolidWorks at startup. The `mcp` 2.x SDK exposes `from mcp.server import MCPServer` as used (PyPI `mcp` latest 2.2.0; [python-sdk README](https://github.com/modelcontextprotocol/python-sdk)).
14. **Per-tool "no session" already exists.** Every tool calls `sw.attach()`, which wraps `win32com.client.GetActiveObject("SldWorks.Application")` and raises `SwNotRunning("SolidWorks is not running. Start SolidWorks, open the document, then retry.")` on `com_error` (`mcp/solidworks/sw.py` lines 22-30). On Windows with `uv` present and SolidWorks closed, the server connects cleanly and each tool returns that message — this is exactly the "quiet when host absent" behaviour, and it already works.
15. **So the red banner is a process-start failure, with two causes.** (a) `uv` missing: the spawn fails and Claude Code reports `✘ Failed to connect — CONNECTION_CLOSED: Connection closed` (observed via `claude mcp list` in this worktree on 2.1.267; `uv` is absent on this machine per `Get-Command uv`, `~/.local/bin`, `~/.cargo/bin`). (b) non-Windows: the environment marker skips `pywin32`, `import pythoncom` raises `ModuleNotFoundError`, the script exits during import, same `CONNECTION_CLOSED`. A first run on Windows with `uv` also needs network to resolve `mcp` and `pywin32` inside `MCP_TIMEOUT` (30 s default, [env-vars](https://code.claude.com/docs/en/env-vars)); not measured.
16. **A second failure inside this repo only.** Because the plugin's `.mcp.json` sits at the repo root, opening the armature repo itself loads the same file as a *project-scoped* server too, where `${CLAUDE_PLUGIN_ROOT}` is not substituted ("Plugin-provided MCP configurations substitute ..." — [mcp#option-3-add-a-local-stdio-server](https://code.claude.com/docs/en/mcp#option-3-add-a-local-stdio-server); missing variables load "with the `${VAR}` text unexpanded" — [mcp#environment-variable-expansion-in-mcp-json](https://code.claude.com/docs/en/mcp#environment-variable-expansion-in-mcp-json)). `claude mcp list` shows both `plugin:armature:solidworks` and `solidworks` failing plus `[Warning] mcpServers.solidworks: Missing environment variables: CLAUDE_PLUGIN_ROOT`. Not the user-facing bug, but it doubles the noise for anyone developing the plugin.
17. **Where the plugin talks about the server.** `skills/init/SKILL.md` step 2 item 2: "On SOLIDWORKS, mention the bundled SolidWorks MCP server (`mcp/solidworks/`; Windows, a running SolidWorks session, and `uv` on PATH) that lets armature-cad's checks run against the live model." `README.md` "SolidWorks MCP (bundled)". `skills/armature-cad/references/solidworks.md` line 65 refers to "the `solidworks` MCP server" by bare key and to tools by short name (`sw_mass_properties(...)`); nothing in `skills/`, `agents/`, or `references/` uses the scoped name `mcp__plugin_armature_solidworks__*`, so moving the server between scopes breaks no matcher. Skill content substitutes `${CLAUDE_PLUGIN_ROOT}` "Anywhere the placeholder appears" — [plugins-reference#environment-variables](https://code.claude.com/docs/en/plugins-reference#environment-variables) — so `init` can write the absolute server path into a project file.

## Options, ranked

Cost is engineering effort in this repo. "Quiet" means a project that is not on SolidWorks sees no MCP failure.

### 1. Opt-in at `init`: move the server out of the plugin's `.mcp.json` into the project (recommended)

Delete the root `.mcp.json`. When the setup interview picks SOLIDWORKS, `init` writes the project's `.mcp.json`:

```json
{ "mcpServers": { "solidworks": { "command": "uv", "args": ["run", "<abs plugin root>/mcp/solidworks/server.py"] } } }
```

with `<abs plugin root>` filled from `${CLAUDE_PLUGIN_ROOT}` (fact 17), and the user approves it once (fact 6). Fusion/Onshape/undecided projects get nothing, so they are quiet by construction; a SolidWorks project on a machine without `uv` still gets one honest failure, which is the right signal there.

- Quiet: yes, for every non-SolidWorks project, with no user action.
- Cost: low. Files: delete `.mcp.json`; `skills/init/SKILL.md` step 2 item 2 and step 3 seeds (write `.mcp.json`, add it to the scoped commit); `README.md` "SolidWorks MCP (bundled)" becomes "SolidWorks MCP (opt-in at init)"; `skills/armature-cad/references/solidworks.md` line 65 unchanged (bare key `solidworks` is what a project-scoped server is called). Tool names become `mcp__solidworks__sw_*`; nothing references the old scoped form.
- Interview wording: "CAD package: SOLIDWORKS / Fusion 360 / Onshape / undecided. On SOLIDWORKS, ask whether to connect the SolidWorks MCP server to this project (Windows, `uv` on PATH; SolidWorks only needs to be running when armature-cad checks the model). Yes writes `.mcp.json`; Claude Code will ask you to approve it on the next start."
- Trade-off: the written path is the versioned cache directory (`.../armature/1.2.1/mcp/solidworks/server.py`), so a plugin update strands old projects until `init`-style rewrite or a documented one-liner; mitigate with option 1b.
- 1b (add-on, medium cost): package `mcp/solidworks/` as a tiny project (`pyproject.toml` + console script) so the entry is path-free: `uvx --from "git+https://github.com/rioharper/armature@v1.2.1#subdirectory=mcp/solidworks" armature-solidworks`. Same `.mcp.json` shape, also suitable for `claude mcp add --scope user`. uv documents `uvx --from git+https://...@<tag>` ([uv tools guide](https://docs.astral.sh/uv/guides/tools/)) and `#subdirectory=` on git sources ([uv dependencies](https://docs.astral.sh/uv/concepts/projects/dependencies/)); the two combined were not exercised here.
- 1c (dev-repo hygiene, trivial): commit `.claude/settings.json` with `"disabledMcpjsonServers": ["solidworks"]` only if the root `.mcp.json` is kept; a rejection "in any settings file applies, including a project `.claude/settings.json` checked into the repository" (fact 4), removing failure 16 for plugin developers. Moot under option 1, which deletes the file.

### 2. Split into a second plugin with `defaultEnabled: false`

Create `plugins/armature-solidworks/` (manifest + `.mcp.json` + `mcp/solidworks/`) and list it in `.claude-plugin/marketplace.json` with `"defaultEnabled": false`; keep `armature` as the skills plugin. Users on SolidWorks run `claude plugin enable armature-solidworks@armature-plugins` (or `/plugin`).

- Quiet: yes, until the user enables it; then it is loud on every project, SolidWorks or not, because plugin enablement is per settings scope, not per CAD choice (fact 2, [settings-reference#enabledplugins](https://code.claude.com/docs/en/settings-reference#enabledplugins)). The user can scope it with `.claude/settings.local.json` per project, which is the same per-project chore as today's `/mcp` toggle.
- Cost: medium. Files: new plugin directory and manifest, `marketplace.json` second entry, move `mcp/solidworks/`, `README.md`, `skills/init/SKILL.md` step 2 wording ("enable the `armature-solidworks` plugin"), `CHANGELOG.md`. Tool names become `mcp__plugin_armature-solidworks_solidworks__sw_*`; nothing references the old form.
- Interview wording: "On SOLIDWORKS: enable the companion plugin with `claude plugin enable armature-solidworks@armature-plugins` (Windows, `uv` on PATH), then restart."
- Extra: relative-path plugin sources "won't resolve" when a marketplace is added by direct URL to `marketplace.json` — [plugin-marketplaces#relative-paths](https://code.claude.com/docs/en/plugin-marketplaces#relative-paths). This marketplace is added from GitHub, so it is fine today.

### 3. Keep the bundle, document the user-side toggle

No code change. Tell users in README and the init interview to open `/mcp` and toggle `solidworks` off in non-SolidWorks projects (fact 3). Cost: trivial. Quiet: only after the user acts, in every single project, and the first session of each project is still red. Rejected as the primary fix; acceptable as a footnote for users who keep the current version.

### 4. Make the server itself start without `uv` or Windows

Not reachable from the config: the only launcher is `command`, and if that executable is missing or the script exits, the result is `CONNECTION_CLOSED` regardless of how the script handles a missing SolidWorks. Two partial hardenings are still worth doing whatever option wins:

- Move `import pythoncom` / `win32com` inside `attach()` (or guard with `try/except ImportError`) so a non-Windows host with `uv` starts the server and gets a per-tool "SolidWorks COM is Windows-only" error instead of an import crash. Cost: trivial; file `mcp/solidworks/sw.py` lines 4-6, 22-30.
- Nothing in Claude Code substitutes a fallback launcher for a missing `uv`; `${VAR:-default}` expansion covers environment variables, not PATH lookups (fact 16 source).

### 5. Lazy connection

Not available for stdio servers in local sessions (facts 8-10). Nothing to change; revisit if the discovery cache is extended to stdio.
